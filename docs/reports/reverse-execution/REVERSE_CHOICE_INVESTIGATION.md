The relevant checks found:

- **Immediate generation:** `MotionStatePlanner.ts:265` initializes FORWARD whenever forward is allowed, regardless of whether the robot is stationary or its first useful move would be reverse. At the first expansion, the analytic connector compares both permitted directions (`:342`, `:683`). Its reverse candidate explicitly contains `DIRECTION_CHANGE → TRANSLATE_REVERSE` and is not gated by the corridor. Separately, lattice transitions generate DIRECTION_CHANGE at the initial pose (`:651`); the reversed search state generates reverse translations when expanded. Thus the primitive reverse move is one search edge after the initial forward state, while the complete reverse connector is evaluated immediately. Initial connector evaluation is limited to 12 m; longer routes rely on the normal search branch first.
- **Guide/heuristic/corridor:** `MotionStateGuide.ts:149` looks up a positional distance field; it does not encode travel direction. Forward and reverse states at the same cell have the same heuristic and corridor membership. The straight reverse connector in this reproduction is compared before frontier dominance checks, and lowering both reverse charges selects it in one expansion. Weighted-A* and first-success corridor termination do not guarantee global optimality in general, but neither explains the observed reproduction.
- **State merging/pruning:** `MotionStatePlanner.ts:143` includes direction in the key, including refined keys. A same-pose FORWARD state does not merge with its REVERSE counterpart. The additional switch cost raises the reverse branch's g/f values; pruning it after a cheaper feasible forward incumbent is found is consistent with these costs. The complete reverse candidate has already been compared at the start.
- **UI mapping:** the editable Reverse risk weight fields (`App.tsx:1595`, `:1611`) write `passageSafety.reverseRiskWeight`. `MotionStateConfiguration.ts:145` maps that directly to `weights.reverseCostPerM`. `weights.directionSwitchCost` comes separately from `passageSafety.motionStateDirectionSwitchWeight` (`:146`), default 1. `updatePassage` merges only the edited fields (`App.tsx:1453`), so changing the reverse risk does not change the switch cost. The switch cost appears in the read-only Effective Motion-State Configuration panel (`App.tsx:130`); there is no corresponding ordinary editable switch-cost field. The legacy `reversePenalty` alias is not the motion-state cost input. `PlanningCoordinator.ts:42` takes a fresh configuration snapshot from the supplied settings; no override or stale-snapshot cause was found in that path.
- **Permission discrepancy worth checking on imported settings:** the UI checkbox displays `allowReverse || backwardAllowed` (`App.tsx:1607`), while the planner uses `backwardAllowed ?? allowReverse`. If an imported configuration has `allowReverse=true` and `backwardAllowed=false`, the UI can appear enabled while effective reverse permission is false. The normal checkbox handler writes both flags together. A regression confirms that the planner honours explicit `backwardAllowed=false`; whether the screenshot has this mismatch is unknown.
- **Goal heading:** `PlanningCoordinator.ts:67` omits the last goal heading unless explicitly requested. An aligned start-to-goal bearing alone is insufficient to guarantee a rotation-free final reverse solution if a different final heading is required. Connector alignment uses a 1e-7 rad tolerance; approximate visual alignment is not sufficient to skip all rotation.
